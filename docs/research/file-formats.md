# Warcraft III file format landscape

Kickoff research mapping the Warcraft III data format landscape for libthunder, a clean-room Warcraft III engine reimplementation in Odin.
Project scope targets the MPQ era of Warcraft III (Reign of Chaos through patch 1.29.2), not the CASC/Reforged era.
Research date: 2026-08-01.
Every claim below is followed by a source URL, or marked `[unverified]` when it could not be confirmed against a primary source.

## Container formats

### MPQ

MPQ (MoPaQ) is Blizzard's archive format and is the container both for the base game's asset archives (`War3.mpq`, `War3x.mpq`, `War3Patch.mpq`) and for individual map files (`.w3x`/`.w3m`) and campaign files (`.w3n`).
Warcraft III uses MPQ format version 1 only (32 byte header, no HET/BET tables, no 64 bit archive size support), across its entire MPQ era from Reign of Chaos through patch 1.29.2.
This is confirmed directly in StormLib's source comments, which document that WC3's `Storm.dll` ignores the header's format-version field and effectively always parses archives as v1, a behavior that "protected" custom maps historically exploited by faking a v2 header to break third-party tools while WC3 itself still loaded the archive as v1 (`src/SFileOpenArchive.cpp`, https://github.com/ladislav-zezula/StormLib).
Format versions 2 to 4 (64 bit offsets, HET/BET tables) were introduced starting with The Burning Crusade and Cataclysm respectively and are WoW-era additions, not used by WC3 (http://www.zezula.net/en/mpq/mpqformat.html).
Compression inside WC3 archives is selected per file via a bitmask compression-type byte: zlib/deflate, PKWARE DCL implode, bzip2, sparse/RLE, and IMA ADPCM mono/stereo for audio sectors; multiple methods can be combined and are decompressed in a fixed order (https://wowdev.wiki/MPQ, itself citing zezula.net and StormLib as its sources).
LZMA and Huffman-for-WAVE are WoW/SC2-era compression options; whether WC3 audio specifically ever uses Huffman rather than plain ADPCM is `[unverified]`.
Encryption covers the hash table, block table, and (optionally) file sector data, each with a key derived from hashing a fixed string or the filename through MPQ's shared hash function, plus optional per-sector Adler32 checksums (mislabeled "sector CRC" in the spec).
The full cipher (a 1280 entry lookup table generated by a fixed-seed LCG, five hash "types" selecting different table segments) is fully specified with worked test vectors on wowdev.wiki, sufficient for an implementer to self-verify without reverse engineering.

Authoritative documentation: Ladislav Zezula's MPQ format page, http://www.zezula.net/en/mpq/mpqformat.html (note: this domain serves a mismatched TLS certificate, issued for `*.nameserver.sk`, so strict HTTPS clients will refuse it; the content itself is live and current, copyright footer dated 2003 to 2011), and a WC3-specific page on map protection at http://www.zezula.net/en/mpq/war3maps.html (more recently maintained, copyright footer 2015 to 2016).
The reference implementation is StormLib, https://github.com/ladislav-zezula/StormLib (actively maintained, latest tag v9.40 published 2026-07-04).
wowdev.wiki's MPQ page, https://wowdev.wiki/MPQ, is a secondary compilation citing the same two sources but is convenient for byte-level tables (note: this site blocks non-browser HTTP clients with a bot challenge; a browser user agent string is required to fetch it).
Documentation quality: complete. The byte-level structures are fully specified with field tables and worked test vectors, and the StormLib source itself functions as the reference implementation the documentation was derived from; no reverse engineering is needed to build an MPQ v1 reader/writer compatible with WC3.

### CASC and the MPQ-to-CASC cutoff

CASC (Content Addressable Storage Container) is the archive format Blizzard introduced in 2014 to replace MPQ, first for other titles and later for Warcraft III (http://www.zezula.net/en/casc/main.html).
The exact patch that switched Warcraft III from MPQ to CASC storage is **patch 1.30.0** (full build string 1.30.0.9900), which first shipped the change in PTR build 9655 and reached retail release on **2018-08-08**.
This is confirmed convergently by three independent sources with no conflict found: Zezula's own CASC overview page states "Warcraft III (since version 1.30, build 9655 PTR)" (http://www.zezula.net/en/casc/main.html); CascLib's own regression test suite hardcodes a test-data entry literally labeled `"Warcraft III/09655"` (`test/CascTest.cpp`, https://github.com/ladislav-zezula/CascLib); and a HiveWorkshop community patch-history thread's table shows patch 1.29.2 (build 9231) as the last entry labeled MPQ and patch 1.30.0 (build 9900) as the first labeled CASC, with an explicit changelog line "transition from MPQ to CASC (from 9655 PTR)" (https://www.hiveworkshop.com/threads/list-of-official-patches-for-warcraft-3.322919/).
The 2018-08-08 release date was independently corroborated via Liquipedia's patch page, https://liquipedia.net/warcraft/Patch_1.30.0.
Practical implication for libthunder: patch 1.29.2 (build 9231) is the last MPQ-era patch; everything from 1.30.0 onward requires a CASC reader instead. This matches the project's stated MPQ-era scope, so CASC support is out of scope but the cutoff is now pinned precisely.

CASC's on-disk local structures (shared-memory `shmem` file, `.idx` journal files, `.XXX` data files) are documented byte-for-byte with worked code at https://wowdev.wiki/CASC, which explicitly scopes itself to the local filesystem format and defers the network/CDN layer to separate TACT (https://wowdev.wiki/TACT) and NGDP pages.
The reference implementation is CascLib, https://github.com/ladislav-zezula/CascLib (actively maintained, latest tag 3.0 published 2026-02-15).
Documentation quality: partial. The mechanical local-storage layer is fully specified, but WC3-specific CASC structure beyond "it uses CASC since 1.30/9655" (e.g. its root/encoding file layout, or whether it uses CASC v1 or v2 semantics) is not separately documented anywhere found; confirming it would require reading CascLib's WC3-specific code paths or reverse engineering against a live Reforged-era install. Irrelevant to libthunder's MPQ-era scope, noted only for completeness.

## Asset formats

### BLP (Blizzard Picture) textures

Purpose: Blizzard's proprietary texture container with precalculated mipmaps, used for nearly all in-game textures (units, terrain tilesets, UI, icons) through the pre-Reforged era.
Base Warcraft III (RoC/TFT) uses BLP0 (beta-era, external mipmap files `.b00` to `.b15`) and BLP1 (retail, internal mipmaps, JPEG or RAW1/palettized content only); BLP2 is a WoW-only variant, not used by classic WC3 (https://www.hiveworkshop.com/threads/blp-specifications-wc3.279306/, cross-confirmed against warcraft-rs's own format documentation stating WoW 1.12.1 to 5.4.8 are "100% BLP2 (no BLP0/BLP1 found)" while WC3 uses BLP0/BLP1, https://raw.githubusercontent.com/wowemulation-dev/warcraft-rs/main/docs/src/formats/graphics/blp.md).
Reforged HD assets reportedly do not use BLP2 either; instead Reforged converts both legacy SD and new HD textures to DDS (BC3-compressed) at build time, with a fallback path that serves a same-named `.dds` if a requested `.blp` doesn't exist, for backward compatibility with custom maps. This is `[unverified at primary-source depth]`, corroborated only via search-engine synthesis of a HiveWorkshop thread that could not be fetched directly this session, not by direct primary fetch. Irrelevant to libthunder's MPQ/pre-Reforged scope regardless.
Best WC3-specific documentation: HiveWorkshop thread "BLP Specifications (WC3)", https://www.hiveworkshop.com/threads/blp-specifications-wc3.279306/, which explicitly frames itself as a correction to prior incomplete/wrong community specs (missing mipmap flag, wrong alpha-bit handling, wrong team-color-blending notes).
wowdev.wiki's BLP page, https://wowdev.wiki/BLP, is the more complete reference for the BLP2/WoW side.
Documentation quality: needs reverse engineering for WC3-specific BLP0/BLP1 detail (the best source is itself a corrective reverse-engineering writeup); comparatively complete for BLP2/WoW, which is out of scope for WC3 anyway.

Open source parsers: zloy-tulen/image-blp (Rust, explicitly targets both WC3 and WoW BLP), https://github.com/zloy-tulen/image-blp. License is declared as MIT only in `Cargo.toml` package metadata; no actual LICENSE file exists in the repository (confirmed via GitHub API contents listing), a nuance worth flagging if reused.
wowemulation-dev/warcraft-rs `wow-blp` crate: dual MIT OR Apache-2.0, confirmed by fetching license files directly (same repo as the MPQ crate above).
WowDevTools/libwarcraft (C#, supports BLP0/1/2 read and write), https://github.com/WowDevTools/libwarcraft. License: GPL-3.0, confirmed via GitHub license API.
Drake53/War3Net `War3Net.Drawing.Blp` module (C#): MIT, confirmed by fetching the LICENSE file directly.
tdauth/wc3lib (C++, includes a BLP codec module): GPL-2.0, confirmed by fetching the `COPYING` file directly; note the maintainer's own README describes the project as "still experimental."

### MDX (binary model) and MDL (text model)

Purpose: MDX is Warcraft III's own binary 3D model format (bones, animation sequences, geosets, particle emitters, cameras, collision shapes) for units, doodads, buildings, and effects; MDL is its human-readable text equivalent with the same logical schema, used for hand editing and diffing. Both are distinct from WoW's M2 (an MDX-lineage successor) and SC2's M3.
Structure at survey level: files start with 4-byte magic `MDLX`, followed by a sequence of independently optional chunks (4-char tag + 4-byte size header, unknown tags skipped by size) in no fixed order. Classic chunk tags include `VERS, MODL, SEQS, GLBS, TEXS, TXAN, GEOS, GEOA, BONE, LITE, HELP, ATCH, PIVT, PREM, PRE2, RIBB, EVTS, CAMS, CLID, SNDS, MTLS`; Reforged adds `CORN` (PopcornFX particle emitters), `FAFX` (FaceFX facial animation), `BPOS` (bind pose matrices), plus `TANG`/`SKIN` sub-chunks inside `GEOS` and a shader-path field in `MTLS` (https://github.com/barncastle/MDXReForged).
Classic RoC/TFT uses `VERS` = 800; Reforged eventually reached `VERS` = 1000. Whether an intermediate `VERS` = 900 existed as an early-Reforged-only value, or was itself the classic value, is `[unverified]`, sourced only from conflicting search-engine synthesis of the same HiveWorkshop thread, which could not be fetched directly this session.
Best documentation: the foundational community spec, Magnus Östberg ("Magos")'s "The MDX file format!", https://www.gamedevs.org/uploads/mdx-warcraft3-file-format.txt, fetched and verified directly; it defines field types and sequential layout but not explicit byte offsets, and virtually every later tool traces back to it.
HiveWorkshop forum thread "MDX Specifications", https://www.hiveworkshop.com/threads/mdx-specifications.240487/, refines Magos's spec and explicitly notes remaining gaps around SND/SNEM/KSPE tracks.
The dedicated HiveWorkshop wiki MDX page (https://wiki.hiveworkshop.com/index.php/MDX_File_Format) could not be reached this session (consistent 502 across multiple attempts, distinct from the ordinary bot-blocking seen on other pages); its live status is `[unverified]`, worth rechecking independently.
Documentation quality: partial. Solid foundational spec for classic MDX (VERS 800); Reforged-era chunks documented piecemeal across forum threads and third-party reverse-engineering repos rather than one canonical source.

Open source parsers: Retera/ReterasModelStudio (Java, editor supporting both classic and Reforged MDX), https://github.com/Retera/ReterasModelStudio. License: MIT, confirmed by fetching the LICENSE file directly.
flowtsohg/mdx-m3-viewer (JS/WebGL, viewer for both WC3 MDX and SC2 M3), https://github.com/flowtsohg/mdx-m3-viewer. License: MIT, confirmed by fetching the LICENSE file directly.
4eb0da/war3-model (TypeScript, MDL/MDX converter and renderer), https://github.com/4eb0da/war3-model. License: MIT, confirmed by fetching the LICENSE file directly.
barncastle/MDXReForged (C#, Reforged-specific reader), https://github.com/barncastle/MDXReForged. No license file found anywhere in the repo; treat as all-rights-reserved by default.
tdauth/wc3lib's MDL/MDX module ("MDLX") is explicitly flagged by its own maintainer as unfinished, per the project's README.

### TGA (Truevision TGA)

Purpose: standard external image format, used by WC3 for the minimap preview image (`war3mapMap.tga`/`war3mapPreview.tga`) and, in beta versions up to 1.21, the pathing map (`war3mapPath.tga`).
No WC3-specific deviation from the public Truevision TGA spec was found; a directly fetched community writeup on the WC3 map format states WC3's usage is "a standard 32bits RGB TGA file with no compression and a black alpha channel," explicitly warning that non-conformant TGA data causes WC3 to misbehave on tilesets (https://867380699.github.io/blog/2019/05/09/W3X_Files_Format).
Reference spec: Truevision TGA File Format Specification v2.0, mirrored at https://github.com/DEAKSoftware/Truevision-TGA (document mirror, not a code library; no license applies since it hosts a decades-old public reference document, not original code).
Documentation quality: complete, minimal WC3-specific research needed; standard TGA decoders (e.g. stb_image) apply directly.

### WAV and MP3 audio

Purpose: WC3 supports only WAV and MP3 natively for imported audio, no OGG or other codec, confirmed via a directly fetched HiveWorkshop thread (https://www.hiveworkshop.com/threads/warcraft-3-audio-formats.308124/).
WAV is used for short SFX and unit response sounds (uncompressed, low latency); MP3 is used for music and ambient loops where file size matters.
Unit replacement sounds specifically require WAV; MP3 is not accepted for that use case, per search-engine synthesis of a separate HiveWorkshop thread, `[unverified at primary-source level]`.
A documented MP3-specific quirk: MP3 encoding inserts silence padding at the start of the file (an MP3 encoder frame-alignment artifact), which breaks seamless music looping; community workarounds use the `SetSoundChannel` or `SetSoundPlayPosition` JASS natives to crossfade or skip the leading silence.
Reforged-era audio codec/backend changes (e.g. whether Reforged moved to Wwise/`.wem`) are `[unverified]`; this could not be researched this session due to web search budget exhaustion. Likely irrelevant to libthunder's MPQ-era scope regardless.
Whether WC3 ships any Bink Video (`.bik`) files (e.g. for intro logos) versus being 100% in-engine cutscenes (MDX/camera/trigger driven) is `[unverified]`.

### SLK (SYLK) and TXT gameplay data tables

Purpose: SLK (Symbolic Link format, an obsolete 1980s Microsoft spreadsheet interchange format, never formally published by Microsoft as a spec) is repurposed by WC3 as the storage format for gameplay object-data tables, e.g. `Units\UnitData.slk`, `Units\UnitBalance.slk`, `Units\UnitWeapons.slk`, extracted from the game's own MPQ archives.
General SYLK record structure: `<RTD>;<FTD>;<data>` lines (Record Type Descriptor + Field Type Descriptor), e.g. `ID` for the file header, `B` for bounds/dimensions, `C` for a cell record with `X`/`Y` sub-fields for column/row position; best available primary doc is Microsoft's own "sylksum.doc", mirrored at https://outflank.nl/upload/sylksum.txt, fetched and verified directly.
WC3's SLK usage is genuine, unmodified SYLK syntax repurposed semantically for game-object rows/columns rather than spreadsheet cells, confirmed by a directly fetched community writeup describing WC3 SLK parsing as reading `ID`, `B;`, `C;Y`, `C;X` prefixed lines (https://867380699.github.io/blog/2019/05/09/W3X_Files_Format).
Column and row counts are strictly enforced and crash-prone: per HiveWorkshop community threads, if actual columns fall short of a declared column count, or the file has more than 96 columns for some files, Warcraft III crashes rather than tolerating the mismatch (https://www.hiveworkshop.com/threads/custom-meta-data-slks.275403/, https://www.hiveworkshop.com/threads/sylk-road.306820/); `[unverified at primary-source depth beyond search-engine synthesis of these threads]`.
"MetaData" SLK files (e.g. `UnitMetaData.slk`) describe the schema of other SLK files, with each field given a 4-character ID and declared type, which the in-game Object Editor uses to render the correct GUI widget.
Companion plain-text TXT files (e.g. `war3mapMisc.txt` for gameplay constants, `war3mapSkin.txt`, `war3mapExtra.txt`) are plain INI format (`[Section]` + `key = value`), not SYLK, confirmed via the same directly-fetched blog post; whether a base-game `UnitBalance.txt` exists distinct from `UnitBalance.slk` was not confirmed and is `[unverified]`.
Documentation quality: partial. The underlying SYLK format is documented (if only via an old Microsoft internal doc mirror); WC3's specific column/row enforcement rules and per-file schemas are known mainly through community forum threads and empirical crash reports rather than a single canonical reference.
Open source parsers: Drake53/War3Net's `War3Net.IO.Slk` module (C#), MIT, confirmed by fetching the LICENSE file directly. tdauth/wc3lib lists SLK/TXT among supported formats, GPL-2.0, confirmed via `COPYING`. No dedicated standalone SYLK-for-WC3 library was found beyond these two general WC3-modding libraries.

### FDF (Frame Definition Format)

Purpose: WC3's UI/menu definition language, defining Frame hierarchies (buttons, dialogs, text, textures) with inheritance, layering, and positioning, used for both the built-in game UI and Reforged-era custom UI modding via natives like `BlzCreateFrame`.
No formal or canonical spec exists; documentation is entirely community reverse engineering, primarily the HiveWorkshop thread "UI: Reading a FDF", https://www.hiveworkshop.com/threads/ui-reading-a-fdf.315850/, fetched and verified directly.
Confirmed structure: optional `IncludeFile "path",` directives; `//` and `/* */` comments; `Frame "FRAMETYPE" "FrameName" { ... }` blocks with comma-terminated property statements; inheritance via `INHERITS "Template"` or `INHERITS WITHCHILDREN "Template"`; top-level "Main-Frames" versus nested child frames; `SIMPLE`-prefixed frame types that render below regular frames and support only Texture/String children; `Layer "BACKGROUND" { Texture ... }` blocks; a 4:3 normalized screen-space coordinate system with origin at bottom-left.
Documentation quality: needs reverse engineering. No BNF-level or byte-level spec was found. No maintained open-source FDF parser was found either (targeted GitHub code search for FDF-specific parsing in War3Net and wc3lib's source trees came up empty); libthunder would need to write one from scratch based on forum-tutorial-level knowledge.

### TOC files

Purpose: plain-text index files listing FDF paths to load; WC3's default is `ui/framedef/framedef.toc`, referencing 75+ built-in FDF files.
Documented at the same forum-tutorial tier as FDF: HiveWorkshop thread "UI: toc-Files", https://www.hiveworkshop.com/threads/ui-toc-files.315854/, fetched and verified directly.
Confirmed structure: one FDF path per line, not case-sensitive; loaded in-game via the native `BlzLoadTOCFile takes string TOCFile returns boolean`; a documented gotcha requires a trailing blank line (at least one for CRLF line endings, at least two for LF), without which loading reportedly failed on Blizzard's own PTR builds.
Documentation quality: needs reverse engineering, same as FDF, though the format is simple enough (a line list plus a blank-line quirk) that a from-scratch parser is low risk regardless of missing prior art.

## Map internals (.w3x/.w3m)

A Warcraft III map file is a custom "HM3W" header prepended to an ordinary MPQ v1 archive, with an optional 260-byte "NGIS" signature footer appended after the MPQ data for TFT-era maps. The internal file names below (`war3map.*`) are the members inside that MPQ. Direct fetches of hiveworkshop.com (both the old MediaWiki wiki and the forum) returned HTTP 403 to every attempt across every research pass this session; the practical replacement that turned out to be fully readable is the GitHub wiki of the HiveWE world editor project, https://github.com/stijnherfst/HiveWE/wiki, which War3Net's own source comments cite as their reference, plus direct reads of parser source code (War3Net, wc3lib, StormLib) via the GitHub API, which worked even where ordinary web fetches were blocked. wc3c.net, the historical host of the original map-format spec, is currently DNS-dead; web.archive.org could not be fetched this session either. Two independent surviving mirrors of the original spec text exist at https://867380699.github.io/blog/2019/05/09/W3X_Files_Format and https://forum.wc3edit.net/viewtopic.php?t=7080.

### The .w3x/.w3m container and the HM3W header

The HM3W header is a 512-byte block: 4-byte magic `"HM3W"`, an unknown int32 (purpose `[unverified]` anywhere; War3Net always writes 0), a null-terminated map name string, an int32 map-flags bitfield, an int32 max-player count, then zero padding out to 512 bytes. The flags bitfield covers things like hiding the minimap in previews, melee-map status, custom forces/techtree/abilities/upgrades toggles, and shore-wave rendering options, and is consistent across the two independent mirror sources and wc3lib's parser (https://github.com/tdauth/wc3lib/blob/master/src/map/w3m.cpp). War3Net writes this header from `war3map.w3i`-derived data on save but never parses it back on load, treating it as a derived/duplicated field rather than a primary source of truth (https://github.com/Drake53/War3Net/blob/master/src/War3Net.Build.Core/Extensions/MapInfoExtensions.cs, verified by direct read).
The MPQ header itself uses the ordinary `"MPQ\x1A"` magic and is nominally located at offset 0x200, but Warcraft III does not check for the formal MPQ "user data" block (`"MPQ\x1B"`) at all, a fact StormLib's own source comments state verbatim: "Note that Warcraft III does not check for user data, which is abused by many map protectors" (`src/SFileOpenArchive.cpp`, https://github.com/ladislav-zezula/StormLib). The engine instead scans for the raw MPQ magic at 512-byte-aligned offsets; War3Net reimplements the identical scan behavior (`TryLocateMpqHeader`, looping in `PreArchiveAlignBytes = 0x200` increments), confirming that "protected" maps exploit this scan tolerance by stuffing garbage into the gap before the real header. The canonical MPQ format spec text itself, "The MoPaQ File Format 1.0" by Justin Olbrantz, is bundled directly in StormLib's repo (https://raw.githubusercontent.com/ladislav-zezula/StormLib/master/doc/The%20MoPaQ%20File%20Format%201.0.txt) since zezula.net's copy could not be fetched this session due to a broken TLS certificate.
Documentation quality: partial. No formal authoritative byte table for the HM3W wrapper specifically exists; the closest thing to a living spec, ChiefOfGxBxL/WC3MapSpecification (https://github.com/ChiefOfGxBxL/WC3MapSpecification), documents only the internal member files and never mentions the HM3W wrapper at all. Whether the wrapper itself changed across RoC/TFT/Reforged is `[unverified]`, an absence of documentation rather than confirmed stasis.

### war3map.w3e (terrain)

Purpose: the terrain grid, one entry per grid corner ("tilepoint"): ground height, water level plus a boundary flag, ground and cliff texture indices, texture variation, cliff layer, and a flags byte (ramp/blight/water/boundary), plus a header giving tileset ID, custom-tileset flag, the ground/cliff tileset lists, and map dimensions/offset.
File magic is `"W3E!"`, one of only a handful of internal files that carries a 4-byte magic at all (alongside `wtg` and the two `.doo` files; `w3i`/`w3r`/`w3c`/`w3s`/`mmp`/`imp`/`wct` start directly with a version int, and `shd` has no header at all).
Documented at https://github.com/stijnherfst/HiveWE/wiki/war3map.w3e-Terrain and, byte-exact and current, in War3Net's source (`MapEnvironmentFormatVersion.cs`, `MapEnvironment.cs`, `TerrainTile.cs`, `TileFlags.cs`, all under https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core, verified by direct read), with wc3lib (https://github.com/tdauth/wc3lib/blob/master/src/map/environment.hpp) as an independent pre-Reforged cross-check.
Two versions exist: v11 (initial, RoC through pre-Reforged) and v12, introduced in patch 2.0.3, not at the 1.32 Reforged launch itself. v12 widens the tilepoint from 7 to 8 bytes by splitting the packed texture-plus-flags byte, expanding the ground-texture index from 4 bits (16 textures max) to 6 bits (64 textures max). The HiveWE wiki page, by contrast, still describes only the 16-texture cap and expresses uncertainty about a v12 ("seems to always be 11? Needs more investigation"); War3Net's serializer, which does explicit bit-shift arithmetic for both versions, is the more trustworthy source for this conflict.
Documentation quality: complete via War3Net's source; the wiki prose is good but stale on the Reforged-era version.

### war3map.wpm (pathing map)

Purpose: the per-cell pathability grid the game actually collides against, at a finer resolution than the `w3e` tilepoint grid; each cell is one flags byte with walkable/flyable/buildable bits plus blight and water bits. (In beta versions up to 1.21 this data shipped as a TGA image instead, `war3mapPath.tga`, with red=walk, green=fly, blue=build, 0=yes and 255=no; see the TGA section above.)
Layout, confirmed directly from War3Net's source (`MapPathingMap.cs`, `PathingType.cs`, `MapPathingMapFormatVersion.cs`, under https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core/Environment, verified by direct read 2026-08-10, copies retained in the git-ignored work/map-reference/): magic `"MP3W"`, int32 version (only v0 exists, "the initial version"; no Reforged-era change), uint32 width, uint32 height, then width*height flag bytes. The flag bits per War3Net's enum: 0x02 walk, 0x04 fly, 0x08 build, 0x20 blight, 0x40 water, 0x80 unknown (named `UNK`); bits 0x01 and 0x10 are unused.
The 2026-08-10 corpus survey (WI-0010) found all 186 stock maps carry the file, every one magic `MP3W` version 0. The cell-grid-to-`w3e`-tilepoint dimensional relationship (like `shd`'s, an off-by-one-prone tilepoint-versus-tile question) is `[unverified]` in the literature and should be pinned empirically against real maps during implementation.
Documentation quality: complete for the container layout via War3Net; the semantics of the 0x80 bit are unknown even to War3Net.

### war3map.w3i (map info)

Purpose: map metadata: name, author, description, recommended player count, camera bounds, playable dimensions, map flags, tileset, loading-screen and prologue-screen text/paths, fog and global-weather settings, sound/light environment, water tint, script language selection, per-player race/controller/start-position/ally-priority data, forces, tech/upgrade availability overrides, and random unit/item tables. This is the single most heavily versioned map subformat.
Fully documented in War3Net's source with explicit version gates on nearly every field: the version enum with patch annotations at `MapInfoFormatVersion.cs`, the gated reader/writer at `MapInfo.cs`, and the flags enum with era comments (bits flagged "TFT only" and "Reforged only") at `MapFlags.cs`, all under https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core/Info, verified by direct read this session. Also documented at https://github.com/stijnherfst/HiveWE/wiki/war3map.w3i---Map-Info, and a 1.31-era version-diff discussion at https://github.com/stijnherfst/HiveWE/issues/59 (note: search engines commonly mis-attribute this issue to a different repository, Drake53/War3Net, which has an unrelated issue at the same number; the correct repository is stijnherfst/HiveWE). wc3lib supports only the RoC-era v18 shape (https://github.com/tdauth/wc3lib/blob/master/src/map/info.hpp).
Version table, confirmed directly from War3Net's enum doc comments: v18 is explicitly labeled "Reign of Chaos format"; v25 is explicitly labeled "The Frozen Throne format"; v28 was "introduced in patch 1.31" (adds `ScriptLanguage`, letting a map select JASS versus Lua, meaning Lua scripting predates the 1.32 Reforged launch by one patch); v31 was "introduced in patch 1.32" (Reforged launch, adds SD/HD support flags and per-player enemy-priority data); v32 was "introduced in patch 2.0.3 PTR"; v33 was "introduced in patch 2.0.3" (adds forced camera zoom bounds). Versions v8/v10/v11/v15/v23/v24/v26/v27 exist for various beta and inter-release states with sparser documentation of their exact provenance.
One conflict was found and resolved in favor of the primary source: a summarized fetch of the HiveWE wiki placed the introduction of fog settings at v25, but War3Net's code unambiguously gates the fog block (`FogStyle`, `FogStartZ`/`EndZ`/`Density`, `FogColor`) at v23, with only the separate `GlobalWeather` field gated at v25; trust the source code over the summarized wiki page.
Documentation quality: complete. Every field's version gate is an explicit conditional in War3Net's reader, leaving no ambiguity about which patch introduced which field.

### war3map.wtg and war3map.wct (triggers)

`war3map.wtg` holds the GUI trigger editor's tree: categories, variables, and trigger definitions, each trigger a list of Event/Condition/Action function calls with typed, possibly nested, parameters. `war3map.wct` holds the JASS source text of any trigger that has been converted to "custom text" mode, in the same order as the wtg trigger list, plus (TFT onward) the map-level "Custom Script Code" comment-and-code pair; it is script bodies specifically, not comments or category names, corroborated by wc3lib's model naming it a plain vector of trigger-text strings (https://github.com/tdauth/wc3lib/blob/master/src/map/customtexttriggers.hpp).
`war3map.wtg` (magic `"WTG!"`) is documented at https://github.com/stijnherfst/HiveWE/wiki/war3map.wtg-Triggers and in War3Net's source (`MapTriggersFormatVersion.cs`, `MapTriggersSubVersion.cs`, `MapTriggers.cs`, under https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core/Script, verified by direct read). `war3map.wct` has no magic bytes at all and no dedicated wiki page anywhere found; it is documented only via War3Net's source (`MapCustomTextTriggersFormatVersion.cs`, `MapCustomTextTriggersSubVersion.cs`, `MapCustomTextTriggers.cs`, same directory).
Versions: `wtg` has FormatVersion v3 (RoC beta), v4 (explicitly labeled "Reign of Chaos format"), v6 (TFT beta), v7 (explicitly labeled "The Frozen Throne format"); `wct` has v0 ("Reign of Chaos format") and v1 ("The Frozen Throne format", which adds the global custom-script pair). Both files additionally gained a separate SubVersion scheme with the 1.31 editor, using sentinel values in place of the plain format-version int (0x80000001 for a beta shape, 0x80000004 labeled "the initial version"), adding per-item type tags and deleted-item tracking for wtg, and switching wct to read entries to end-of-file rather than a leading count. No Reforged (1.32+) format bump was found for either file, a deliberate negative finding: the trigger file formats have been structurally stable since patch 1.31.
Documentation quality: complete for `wtg` via War3Net's reader; `wct`'s byte layout is equally complete from source but has essentially no prose documentation anywhere, closest to needing reverse engineering of the files in this group if War3Net's source were unavailable.

### Object data files: war3map.w3u, .w3t, .w3b, .w3d, .w3a, .w3h, .w3q

The extension-to-meaning mapping was verified precisely against War3Net's own filename constants (each object-data class declares its own `war3map.*` filename literal), independently cross-checked against the HiveWE wiki's file table and wc3lib's `typeByExtension` map: `.w3u` is units, `.w3t` is items, `.w3b` is destructables, `.w3d` is doodad *type/object-editor definitions* (not placement; placement lives entirely separately in `war3map.doo`), `.w3a` is abilities, `.w3h` is buffs/effects (War3Net's class is literally named `BuffObjectData`, keyed to `Units\AbilityBuffData.slk`), and `.w3q` is upgrades. All seven filename constants live under https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core/Object, each also declaring `war3campaign.*`, `war3mapSkin.*`, and `war3campaignSkin.*` variants, confirming the existence of Reforged-era "skin" companion files (see below).
One direct conflict was found in the wild and should be disregarded: a search-engine summary of the Ice-Sickle project's wiki produced a completely different mapping (`.w3t` as tileset, `.w3b` as building, `.w3d` as destructible, `.w3h` as hero, `.w3q` as item), contradicting every authoritative source above (War3Net, HiveWE, wc3lib all agree with each other). The Ice-Sickle wiki page is a placeholder in an archived repository and the summary tool's output may be garbled; treat that mapping as unreliable and rely on the verified one instead.
Shared structure: an int32 format version, then an "original objects" table (modifications to Blizzard's standard entries) and a "custom objects" table (new entries, tracking both old and new IDs), each a list of per-field modifications keyed by a 4-character modification ID plus a typed value; `.w3u`/`.w3t`/`.w3b`/`.w3h` use a simple shape, while `.w3a`/`.w3q` add a level/variation index and a data pointer (for `.w3a`, selecting which SLK data column, skipping column E) and `.w3d` similarly adds a variation index.
Versions: v1 (obsolete/hidden), v2 ("the initial version", i.e. RoC/TFT-era per wc3lib's independent labeling), and v3, introduced specifically in patch 1.33 rather than at the 1.32 Reforged launch (https://github.com/Drake53/War3Net/blob/master/src/War3Net.Build.Core/Object/ObjectDataFormatVersion.cs, verified by direct read). v3 introduces per-object "sets", i.e. multiple modification sets per object, plausibly corresponding to SD/HD/teen asset modes.
This v3 multi-set structure is the most load-bearing finding in this section for a from-scratch parser: wc3lib parses it correctly as a repeated per-set loop (https://github.com/tdauth/wc3lib/blob/master/src/map/customunits.cpp, whose own comment cites the HiveWE wiki as its source), but both War3Net and WC3MapTranslator (https://github.com/ChiefOfGxBxL/WC3MapTranslator/blob/master/src/translators/ObjectsTranslator.ts) read only a flat, single-set shape, correct only when a given object has exactly one modification set and silently wrong otherwise. Implement the wc3lib/HiveWE per-set loop, not the War3Net/WC3MapTranslator flat shape.
The Reforged skin-file split is concretely confirmed: WC3MapTranslator's destructable field list carries a comment that fields flagged `netsafe=1` in `destructablemetadata.slk` are written to the separate `war3mapSkin.w3b` file instead; the HiveWE wiki dates this split to patch 1.33 and speculates it exists specifically to keep netsafe fields out of the map's checksum computation.
Documentation quality: complete for the field-level shape, via War3Net plus wc3lib as an independent cross-check; the v3 multi-set handling specifically needed cross-referencing two disagreeing implementations to resolve correctly, which is the closest thing to a genuine gap in this group.

### war3map.j (map script)

Purpose: the map's executable JASS source, plain text with no binary structure. For GUI-authored maps it is generated by the World Editor from `wtg` plus `wct` (plus `wts` for `TRIGSTR_*` resolution); hand-written scripts ship directly as this file.
Both a root-level path (`war3map.j`) and an alternate archive path (`scripts\war3map.j`) occur in real maps and are both handled by War3Net's MPQ writer (https://github.com/Drake53/War3Net/blob/master/src/War3Net.Build.Core/Script/JassMapScript.cs, verified by direct read). The Reforged-era alternative is `war3map.lua` / `scripts\war3map.lua`, mutually exclusive with the JASS file and selected by `w3i`'s `ScriptLanguage` field, available starting at `w3i` format v28 (patch 1.31), one patch before the Reforged launch proper. The GUI-to-script generation pipeline is implemented in https://github.com/Drake53/War3Net/blob/master/src/War3Net.Build/MapScriptBuilder.cs.
Documentation quality: complete as a container (it is simply a text file); the JASS language itself is covered separately above.

### war3map.wts (trigger strings)

Purpose: a plain-text localization table, entries of the form `STRING <n>` with an optional comment and a `{ ... }` body; `TRIGSTR_<n>` placeholders elsewhere (in `w3i`, `wtg`, etc.) resolve against this file.
Documented directly from War3Net's source: the filename constant (plus a `war3campaign.wts` variant) and text-mode parser at https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core/Script (`TriggerStrings.cs` and its text-serialization counterpart), verified by direct read.
No version field exists; the format has been stable since Reign of Chaos with no Reforged-era change found.
Documentation quality: complete, and structurally trivial compared to the rest of this group.

### war3map.w3c (cameras)

Purpose: named editor camera presets usable from triggers: target x/y, z offset, rotation, angle of attack, distance, roll, field of view, far clip plane, plus (Reforged) local pitch/yaw/roll.
No wiki page for this format was found readable anywhere; documentation is War3Net and wc3lib source only (`MapCamerasFormatVersion.cs`, `Camera.cs`, `MapCameras.cs` under https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core/Environment, verified by direct read; wc3lib implements only the older 9-float shape at https://github.com/tdauth/wc3lib/blob/master/src/map/camera.hpp).
The version field itself never changed (only v0, labeled "the initial version", was ever found), which makes this format's one real quirk especially notable: the Reforged-era extension to 12 floats (adding local pitch/yaw/roll) is not signaled by any version bump at all. War3Net detects it by attempting to parse the new, longer shape and falling back to the old shape on failure. The exact patch that introduced the extra floats is `[unverified]`; a HiveWorkshop thread specifically about parsing old-versus-new `war3map.w3c` files exists (https://www.hiveworkshop.com/threads/parsing-old-new-war3map-w3c-files.328473/) but could not be fetched this session (403).
Documentation quality: needs reverse engineering specifically for the old/new discrimination heuristic; the field lists themselves are solid, with wc3lib's 9 floats matching War3Net's old-format shape field for field.

### war3map.w3r (regions)

Purpose: named rectangular regions for triggers: bounds (4 floats), name, a creation number, a 4-character weather-effect ID, an ambient sound name (referencing `war3map.w3s`), and an editor display color.
Documented at https://github.com/stijnherfst/HiveWE/wiki/war3map.w3r-Regions and in War3Net's source (`MapRegionsFormatVersion.cs`, `Region.cs`, `MapRegions.cs`, under https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core/Environment, verified by direct read, including a check for a `"FUCK"` map-protection signature some tools inject), with wc3lib as an independent cross-check (https://github.com/tdauth/wc3lib/blob/master/src/map/rects.hpp, latest version 5).
Per the HiveWE wiki, versions build up incrementally: v1 used integer coordinates with no extra fields, v2 switched to float coordinates, v3 added the weather-effect ID, v4 added the ambient sound reference, and v5 added the display color; which versions correspond specifically to RoC versus TFT is `[unverified]`, and no Reforged-era bump was found.
A genuine parser trap was found and is worth flagging directly: War3Net's region reader reads all fields unconditionally regardless of the declared version, even though its own version enum accepts the older v2/v3 values, meaning it would misparse a genuinely old, shorter file if one were encountered; whether such files exist in the wild is `[unverified]`.
Documentation quality: complete for the field list; the version-gating gap in the most complete available reader implementation is a concrete risk worth designing around rather than copying.

### war3map.w3s (sounds)

Purpose: sound definitions referenced by triggers (`gg_snd_*` handles): name, file path, an EAX preset string, flags (looping, 3D, music, etc.), fade in/out, volume, pitch, channel, and 3D distance/cone parameters; Reforged adds dialogue and facial-animation metadata.
Documented at https://github.com/stijnherfst/HiveWE/wiki/war3map.w3s-Sounds and in War3Net's source (`MapSoundsFormatVersion.cs`, `Sound.cs`, under https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core/Audio, verified by direct read), with wc3lib covering only v1 (https://github.com/tdauth/wc3lib/blob/master/src/map/sound.hpp).
Versions: v1 ("the initial version"), v2 ("introduced in patch 1.32", adding a repeated name/path pair, an SLK display-name string, dialogue text/speaker keys, and FacialAnimation label/group/set-path fields), and v3 ("introduced in patch 1.32.6", adding one trailing unknown int32). Note this format's revision cadence (1.32 and 1.32.6) differs from `w3e`/`w3i`, which instead bumped at patch 2.0.3, illustrating that per-file version cadence is genuinely independent across the map subformats and cannot be assumed to track a single "map format version" number.
Documentation quality: complete via War3Net, including a self-consistency check that the v2 shape's repeated name/path strings actually match, an odd but verified quirk of that layout.

### war3map.shd (shadow map)

Purpose: a baked terrain shadow mask, one byte per sample (0xFF shadowed, 0x00 not), at a density of 16 samples (a 4x4 grid) per `w3e` terrain tilepoint; the file carries no width/height of its own, so dimensions must be derived from `w3e`.
Documented in War3Net's source (a single byte list read to end-of-file, https://github.com/Drake53/War3Net/blob/master/src/War3Net.Build.Core/Environment/MapShadowMap.cs, verified by direct read) and in wc3lib (https://github.com/tdauth/wc3lib/blob/master/src/map/shadow.hpp, which documents the 4x4-per-tilepoint density). A HiveWorkshop wiki page exists (https://wiki.hiveworkshop.com/index.php/War3map.shd_File_Format) but could not be fetched this session (403), so its content is `[unverified]`.
This is a verified negative worth calling out: `shd` has no header, no magic, and no version field at all, unlike almost every other file in this group.
Documentation quality: complete for the general shape; the exact byte-count arithmetic relative to `w3e`'s tilepoint-versus-tile convention (an off-by-one-prone relationship) is `[unverified]` and would need checking against a real extracted map file before relying on it.

### war3map.mmp (minimap preview icons)

Purpose, verified precisely, resolving what could otherwise be a naming ambiguity: static, editor-authored minimap preview icons only, gold mines, neutral buildings, and player start locations, shown on the map's static preview image. This is explicitly not player pings, which are transient network messages never persisted to any file. War3Net's own enum names confirm this directly (`GoldMine`, `NeutralBuilding`, `PlayerStartLocation`, https://github.com/Drake53/War3Net/blob/master/src/War3Net.Build.Core/Environment/PreviewIconType.cs, verified by direct read), and wc3lib independently agrees, naming its equivalent class `MenuMinimap` with the description "the menu minimap of a Warcraft III map which contains special markers" (https://github.com/tdauth/wc3lib/blob/master/src/map/menuminimap.hpp).
Layout: int32 version, int32 count, then per icon an int32 type, int32 x, int32 y, and a color. Only version 0 has ever been found in either source; no Reforged-era change exists.
Documentation quality: complete for the layout, from two independently agreeing sources, though no prose wiki page for this format was located anywhere.

### war3map.imp (imported files manifest)

Purpose: a manifest of custom imported assets: int32 version, int32 count, then per entry a flags byte plus a full path string; the flags byte distinguishes a "standard" import path (auto-prefixed with `war3mapImported\`) from a custom full path.
War3Net documents the container shape (https://github.com/Drake53/War3Net/tree/master/src/War3Net.Build.Core/Import, covering both `war3map.imp` and the campaign equivalent `war3campaign.imp`) but names the flag bits `UNK1` through `UNK16`, i.e. explicitly unknown, verified by direct read. The only semantic clue for the flag byte anywhere found is an attributed community comment in wc3lib crediting a contributor by forum handle: "tells if the path is complete or needs 'war3mapImported\' (5 or 8 = standard path, 10 or 13: custom path)" (https://github.com/tdauth/wc3lib/blob/master/src/map/importedfiles.hpp).
Only one version (v1) has ever been found; no Reforged-era change exists.
Documentation quality: the container layout is complete, but the flags-byte bit semantics need reverse engineering; only a handful of empirically observed values exist anywhere in the literature, with no bit-level breakdown.

### war3mapUnits.doo and war3map.doo (placement)

`war3mapUnits.doo` (capital U, confirmed identically across War3Net's filename constant, wc3lib's class, which is literally named `UnitsAndItems`, and the HiveWE wiki page title) holds placed instances of both units and items in one flat list, disambiguated by which SLK the entry's 4-character type ID resolves against; this is a separate concern entirely from the `.w3u`/`.w3t` type *definitions* discussed above, confirmed structurally by every parser keeping them in separate classes/namespaces. Per-entry fields include type ID, variation, position, rotation, scale, (Reforged) a skin ID, flags, owning player, HP/MP overrides, item-drop tables, gold amount, target-acquisition setting, hero level/strength/agility/intelligence, starting inventory, modified abilities, custom player color, waygate destination, and a creation number.
`war3map.doo` (all lowercase) holds placed instances of doodads and destructables together in a single list, with no separate destructable-placement file existing at all; the HiveWE wiki states this outright ("The file contains the definitions for all doodads including destructables", https://github.com/stijnherfst/HiveWE/wiki/war3map.doo-Doodads), and it is corroborated structurally by War3Net having no destructable-placement class whatsoever and by the doodad placement entry carrying item-drop-on-death tables, which are only meaningful for destructables. `war3map.doo` also carries a second, separate section of cliff-attached "special" terrain doodads (non-editable), its own tiny format with its own always-v0 version field.
Both files share the magic `"W3do"` and the same version scheme, whose enum doc comments name both files explicitly: v6 (RoC beta), v7 (RoC), v8 (TFT), with a SubVersion field further distinguishing 7/9/10/11 (the HiveWE wiki itself hedges on whether 11 is specifically the TFT value). The Reforged-era addition of a per-entry skin ID field to both files is, like `w3c`'s camera extension, not signaled by any formal version bump at all; War3Net detects its presence by byte-sniffing the next value rather than reading a flag, and wc3lib's own source carries a maintainer TODO comment admitting its Reforged support here is incomplete, deferring instead to WC3MapTranslator's implementation.
Documentation quality: complete for RoC/TFT via the HiveWE wiki's full byte layout and War3Net's source; partial for the Reforged skin field specifically, whose only known detection method is a heuristic rather than a formal signal.

## JASS

### Language semantics

JASS ("Just Another Scripting Syntax") is a statically-typed, Java/Ada-inspired procedural scripting language Blizzard built for WC3, later reused in modified form for StarCraft II's Galaxy.
The most substantive community spec is "The JASS Manual" by Jeff Pang (2003), https://jass.sourceforge.net/doc/, including a genuine semi-formal EBNF grammar at https://jass.sourceforge.net/doc/bnf.shtml (fetched and verified directly), covering programs, declarations, statements, and expression precedence. The manual is licensed GNU FDL 1.2 (https://jass.sourceforge.net/doc/license.shtml), i.e. freely redistributable and modifiable documentation, and explicitly self-describes as unofficial and possibly incomplete.
The modern, most authoritative native-level (API surface) reference is jassdoc, https://github.com/lep/jassdoc, maintained by community member "lep": a verbatim, annotated copy of Blizzard's actual `common.j`/`Blizzard.j` with Javadoc-style `@param`, `@bug`, `@note`, `@pure`, `@async`, `@event`, and `@patch` tags layered on top, compiled into a queryable SQLite database (searchable via the third-party front-end Jassbot, https://lep.nrw/jassbot/).
vJass is an unofficial, separate preprocessor/superset layered on top of vanilla JASS by Vexorian, compiled via the JassHelper tool down to plain JASS before the game ever sees it; the engine itself has zero vJass awareness, so JASS VM quirks documented below apply equally to code emitted by JassHelper. The canonical manual (mirrored at https://github.com/wurstscript/WurstScript/blob/master/Wurstpack/vexorianjasshelper/jasshelpermanual.html, fetched and parsed directly, 4288 lines) covers libraries, structs, interfaces, modules, text macros, and script optimization. Its original canonical host, wc3c.net, is currently unreachable (DNS resolution failure); a maintained fork of the abandoned original tool exists as "C-JassHelper" at https://c-jasshelper.sourceforge.net/.
Documentation quality: complete for vanilla JASS syntax and grammar (a real BNF exists); complete for vJass as a preprocessor concept (one authoritative manual, if only survivable via mirrors); the native API surface itself (what each native actually does) is documented incrementally and empirically via jassdoc rather than an official Blizzard reference, since Blizzard never published one.

### common.j and Blizzard.j

`common.j` is the native/type declarations file bundled inside WC3's own MPQ archives (path `Scripts\common.j`), declaring every engine native function signature and base type (`unit`, `player`, `timer`, `agent`, `widget`, etc.) with no function bodies, analogous to a C header.
`Blizzard.j` is the second bundled file implementing the "BJ" (Blizzard-JASS) wrapper functions that the World Editor's GUI trigger system calls under the hood; unlike common.j's bare native declarations, BJ functions have real bodies (ordinary JASS) that typically call one or more common.j natives plus bookkeeping logic, e.g. tracking "last created unit" for GUI's convenience references.
The best current canonical, documented copies of both files live in jassdoc, https://github.com/lep/jassdoc (`common.j` and `Blizzard.j` at the repo root, verbatim Blizzard text with annotations layered on top); the jassdoc repository itself has no LICENSE file (confirmed via GitHub API), so it is technically all-rights-reserved by default, though openly cloned and actively maintained in practice.
No explicit Blizzard statement authorizing redistribution of common.j/Blizzard.j was located; observed community practice (jassdoc's public repo, HiveWorkshop threads soliciting per-patch copies as forum attachments) shows unambiguous tolerance-by-convention, but the underlying legal status is `[unverified]`, a fact-finding note rather than legal advice.
Per-patch copies are actively collected by the community specifically because the files change between patches: see HiveWorkshop threads "All common.j" (started by jassdoc's own author explicitly soliciting old per-patch copies to track native-addition history, https://www.hiveworkshop.com/threads/all-common-j.321388/) and "Latest .j files (1.32.2)" (https://www.hiveworkshop.com/threads/latest-j-files-1-32-2.322942/).

### Known JASS VM quirks

Handle ID reuse: JASS handles are reference-counted; jassdoc's own annotation on `GetHandleId` (fetched directly from its `common.j` copy) documents that removing a game object does not invalidate its allocated handle ID, that handle IDs can differ between clients, and that the returned index "is only a weak and not a conclusive indicator of leaking game objects." Related HiveWorkshop threads document that `I2H` (integer-to-handle conversion) does not increase a handle's reference count, making it possible for the returned handle to be recycled/invalid, and that the community recommendation is to avoid `I2H` entirely (https://www.hiveworkshop.com/threads/typecasting.232039/).

Hashtables: a per-map limit of approximately 255 hashtable instances is repeatedly and consistently cited across HiveWorkshop threads (https://www.hiveworkshop.com/threads/hashtable-limit.156351/, https://www.hiveworkshop.com/threads/single-hashtable-limits.277403/). Implementation-internals claims (array-of-linked-lists bucket structure, performance degradation at very large entry counts) are `[unverified]`, sourced only from aggregated search-engine snippets rather than a fetched primary thread.

Memory leaks: the canonical community tutorial is "Things That Leak" by HiveWorkshop user Ralle, originally posted 2007-06-10, fetched and verified directly (https://www.hiveworkshop.com/threads/things-that-leak.35124/). It documents that unit groups, locations (`(Position of...)`/`(Center of...)`), player groups/forces, and special effects all leak handles unless explicitly destroyed (`DestroyGroup`, `RemoveLocation`, `DestroyForce`, explicit special-effect `Destroy`), explicitly warns that `(All Players)` does not leak and destroying it can cause problems, and blacklists specific GUI actions ("Pick all units of type X", "Pan Camera as needed") as always-leaking. Timer leaks (failing to `PauseTimer`/`DestroyTimer`) are extremely well established community knowledge but were not independently verified against a specific fetched primary thread this session, `[unverified at that level of specificity]`.

Desyncs: the canonical reference is "Known causes of desync" by HiveWorkshop user Ricola3D, posted 2019-07-27, fetched and verified directly (https://www.hiveworkshop.com/threads/known-causes-of-desync.317486/). It tiers causes by confidence: guaranteed desyncs include using `GetLocalPlayer()` for anything beyond local UI/sound, the GUI action aliased `SelectGroupForPlayerBJ`, and the GUI action aliased `SmartCameraPanBJ` (the latter fixed in patch 1.31); lower-probability causes include specific weapon-upgrade interactions and short-period timers created at map init; and a cross-referenced list of `@async`-tagged natives from jassdoc (functions whose return values are not guaranteed synchronized between clients, e.g. `GetLocalPlayer`, `GetCameraTargetPositionX/Y/Z`, `GetUnitName`, `GetLocationZ`) is called out as the general category to avoid using for anything that affects simulation state.

Crashes: the canonical reference is "List of WarCraft III Crashes" by HiveWorkshop user Bribe, posted 2011-05-04, fetched and verified directly (https://www.hiveworkshop.com/threads/list-of-warcraft-iii-crashes.194706/). Notable script-adjacent items: saving certain GUI hashtable value types not present in the Variable Editor (e.g. "ability", "trackable") crashes the World Editor itself; severe memory leaks can escalate to a hard game crash via pagefaults, not just desyncs; self-retriggering order-event triggers can infinite-loop. A cross-referenced external wc3c.net bug list could not be verified as still live (wc3c.net's DNS is currently failing).

TriggerEvaluate/TriggerExecute: per jassdoc's annotations (fetched directly), `TriggerEvaluate` runs every condition function attached via `TriggerAddCondition` with no short-circuiting (use `And`/`Or` natives for that), and returns `false` if a condition function crashes its execution thread or fails to return a value; `TriggerExecute` runs a trigger's actions in a new execution context and blocks the caller until the trigger finishes or suspends via `TriggerSleepAction`. Both natives start a new JASS execution thread, which is why the community documents restrictions on combining them with sleep/wait natives inside the callee.

### Open source JASS parsers and interpreters

corepunch/open-realm, https://github.com/corepunch/open-realm, is the closest prior art to libthunder itself: a C reimplementation of the WC3 engine, described in its own README as loading and rendering original game assets directly from `War3.mpq` (v1.0 to v1.29b), with a from-scratch bytecode-compiling JASS VM ("libjass": lexer, parser, codegen, opcode table, at `games/warcraft-3/jass/`). License: MIT, confirmed by fetching the LICENSE file directly. The repository's `pushed_at` timestamp from the GitHub API is 2026-08-01 (today), i.e. under active development, not abandoned. Worth a dedicated read of its JASS VM architecture before libthunder locks in its own design.

lep/pjass, https://github.com/lep/pjass, is a fast bison/yacc-based JASS2 syntax checker (return-bug detection, string-hash collision detection, variable-shadow detection) but does not execute code; not a VM. License: BSD-2-Clause, confirmed via fetched LICENSE content.

sumneko/JassParser, https://github.com/sumneko/JassParser, a Lua-based JASS-to-Lua-AST parser by the author of `lua-language-server`. License: GPL-3.0, confirmed via GitHub license API (metadata check, not raw-file fetch).

zach-cloud/JAST, https://github.com/zach-cloud/JAST, a Java AST-based static analysis and script-editing tool (merges/dedups war3map.j files, renames symbols safely, brute-forces StringHash collisions), explicitly not an interpreter/VM; shells out to PJASS for syntax checking. ### Per-patch API variance

Directly confirmed by parsing jassdoc's `@patch`-annotated `common.j` (primary-source data, not search-aggregated): natives were added across many patches, not just at launch, with `@patch` tags spanning 1.00 through Reforged build 2.0.3.22904. A rough per-version-bucket count of natives introduced (automated proximity-matching over free-form doc comments, directionally correct but not exact) shows substantial jumps at 1.00 (790 natives at launch), 1.07 (174), 1.24a (103), 1.29 (99), 1.31 (196, the patch that added hashtables), and 1.32 (78), confirming the well-known community claim that the native API grew meaningfully well past initial release, continuing into the Reforged era.
`common.j` and `Blizzard.j` themselves change per patch: confirmed structurally by the existence of active community threads specifically hunting down "the current patch's" copy of each file (see previous section), though no byte-level diff between two patch versions was performed this session, so the exact nature of what changes is `[unverified]` beyond "that it changes."
Reforged added an alternative, mutually exclusive Lua 5.3 scripting VM at the map level (a map picks either JASS/vJass or Lua, not both); this did not deprecate the JASS VM, so common.j's native growth continues to apply to the JASS-mode path specifically. `[unverified beyond search-engine synthesis]`

## Replays

### .w3g structure

`.w3g` is a bespoke custom binary format, not an MPQ archive: files start with a 28-byte zero-terminated ASCII string `"Warcraft III recorded game\x1A\0"`, not the MPQ magic bytes. Confirmed directly from the canonical community spec `w3g_format.txt` v1.18 (2007-06-26, authors "blue, nagger"), mirrored and fetched directly at https://github.com/scopatz/w3g/blob/master/w3g_format.txt.
Structure: a fixed main header (file offset of the first compressed block, overall compressed size, header-version flag, decompressed size, block count) followed by a version-dependent sub-header (a pre-1.07 8-byte layout versus a post-1.07 12-byte layout that adds a `'WAR3'`/`'W3XP'` product identifier), then a sequence of independently zlib-compressed data blocks (each roughly 8KB decompressed, Z_SYNC_FLUSH boundaries).
What gets recorded: game setup (host player record, game name, packed `GameSettings` bitfields covering speed/visibility/observers/teams/shared-control/random-hero/random-races/referees plus a map checksum, per-player `SlotRecord`s, and a `RandomSeed`), then a variable-length body of time-incremented action blocks (per-player recorded commands), interleaved chat-message blocks (added 1.07+), periodic checksum/seed-sync blocks, leave-game blocks, and a forced-game-end block. `RandomSeed` for custom games is the host client's process uptime in milliseconds; for ladder games it is server-assigned and its exact derivation is undocumented by the spec itself.
A companion document, `w3g_actions.txt` (same authors, v1.01), covers the per-action-ID byte layout for the recorded commands (ability casts, unit orders, selection changes, hotkeys, cheats, pings, chat) and documents several version-gated action-format changes, e.g. new fields added to several action IDs at patch 1.07 and a restructuring at patch 1.14b that shifted subsequent action IDs.
The spec's own version table enumerates every RoC/TFT patch from 1.00 (2002-07-03) through 1.21b (2008-02-06) with replay-version numbers, build numbers, and dates, and explicitly flags patch 1.14/1.14b as the one case where replays are cross-incompatible despite being a minor version bump; `SlotRecord` itself grew from 7 to 8 bytes at patch 1.03 (added AI-strength) and to 9 bytes at patch 1.07 (added handicap).
Reforged (2019+) broke the classic spec and no official Blizzard documentation for the new format exists: confirmed via two official Blizzard forum threads where community developers explicitly requested published specs and received no committing response (https://us.forums.blizzard.com/en/warcraft3/t/specs-for-replay-format-reforged/4015, https://us.forums.blizzard.com/en/warcraft3/t/replay-format-change-documentation/28135, the latter stating outright "the replay format has had a few minor (but breaking) changes that we've had to manually reverse engineer"). A maintained modern parser (w3gjs) encodes this reverse engineering as version-gated branches in source rather than from written docs, e.g. the observer team ID changes from 12 to 24 once the subheader version reaches 29, and Reforged adopted a distinct "2.x" version numbering scheme separate from the classic 1.x numbers the 2007 spec documents (`src/W3GReplay.ts`, `src/convert.ts`, https://github.com/PBug90/w3gjs).
Documentation quality: complete for RoC/TFT through roughly patch 1.21b (thorough, field-by-field, with an explicit per-patch version table); needs reverse engineering for the Reforged era, where no written spec exists and every actively maintained parser encodes the differences as empirically derived version branches.

Open source parsers: PBug90/w3gjs (TypeScript/JS, actively maintained, last push 2026-07-28), https://github.com/PBug90/w3gjs. License: MIT, confirmed by fetching the LICENSE file directly; its own README states replays from patch 1.14 and earlier are not fully supported even by this actively maintained parser.
scopatz/w3g (Python), https://github.com/scopatz/w3g, also the canonical current host of the original spec text. License: CC0-1.0 for the repository, confirmed by fetching the LICENSE file directly; note this CC0 declaration is the mirror maintainer's own choice for the repo and does not necessarily re-license the original 2007 spec authors' narrower "free to copy unchanged, credit us" terms carried in the spec text's own header, so the copyright status of the prose spec itself is `[unverified]` beyond what its own disclaimer states.
efskap/warcrumb (Go), https://github.com/efskap/warcrumb, explicitly claims Reforged support with its own original reverse-engineering research (e.g. Battle.net 2.0 integration fields). License: GPL-3.0, confirmed via GitHub license API.
Drake53/War3Net's replay module (C#), https://github.com/Drake53/War3Net, a fairly complete from-scratch reimplementation (dedicated classes for the header, action blocks, timeslot blocks, player/slot records, encoded strings). License: MIT, confirmed by fetching the LICENSE file directly.
whage/w3g-parser (Go) and OttoAllmendinger/libw3g (JavaScript and Python, not C as some secondary sources mislabel it, confirmed via GitHub's own language-breakdown API) and aesteve/w3rs (Rust, Reforged-only, self-described as a "week-end experiment") all have no LICENSE file present in their repositories, confirmed via GitHub API and root listings; treat as all-rights-reserved by default. No maintained plain-C (not C++/C#) w3g parser was found.

## Campaigns and saved games

### .w3f and .w3n

`.w3n` is a genuine MPQ archive (unlike `.w3g` above): it carries the same 512-byte header and 260-byte authentication footer as `.w3x`/`.w3m` map files, wrapping an MPQ that can contain `war3campaign.w3u/.w3t/.w3a/.w3b/.w3d/.w3q/.w3f` object-data files (the campaign-scoped equivalents of a map's object data) and `war3campaign.imp`, confirmed via a directly fetched community writeup (https://867380699.github.io/blog/2019/05/09/W3X_Files_Format, itself a mirror of an original wc3c.net article by "Zepir"). `.w3n` only exists for TFT-based campaigns per a secondary fileformat.com summary, `[unverified firsthand]`.
`.w3f` is the campaign info file inside a `.w3n` archive (`war3campaign.w3f`): file-format-version, campaign-version, editor-version, campaign name/difficulty/author/description strings, a version-gated fog-settings block, background/minimap/ambient-sound paths, and arrays describing chapter titles, per-map entries, and map-order/attack-wave structures. Cross-verified against actual reimplementation source code (`CampaignInfo.cpp` in a `w3f`-branch fork of the HiveWE world editor, https://raw.githubusercontent.com/BogdanW3/HiveWE/w3f/src/Base/CampaignInfo.cpp), which appears to contain a genuine bug (a map-transitions loop iterating over the wrong array), itself informative about the maturity of even the best available reimplementation.
Documentation quality: confirmed, not assumed, to be meaningfully thinner than the standard map format. The dedicated Luashine/wc3-file-formats documentation project (https://github.com/Luashine/wc3-file-formats, no LICENSE file, confirmed via GitHub API) lists "all the custom campaign stuff" among its own not-yet-done goals, and its progress tracker marks `.w3f` status as a single line, "transcribed", versus much more detailed per-field notes for standard map files. A separate umbrella spec project, ChiefOfGxBxL/WC3MapSpecification (MIT, confirmed via GitHub API), has folders for every standard map subformat but none for the campaign format at all. By contrast, the standard map format has multiple independent, cross-checked documentation efforts (see Map internals section).
Open source tooling: Drake53/War3Net (C#), https://github.com/Drake53/War3Net, has dedicated campaign-info classes and full MPQ support for reading `.w3n` containers; its own README states an ambition of covering "every file format... RoC through Reforged." License: MIT, confirmed by fetching the LICENSE file directly.

### Saved games (.w3z)

The saved-game file extension is `.w3z`, per multiple converging secondary sources (a fileformat-reference site, and several HiveWorkshop thread titles referencing "Save (.w3z) Editing", `[unverified firsthand]` since HiveWorkshop's own pages could not be fetched directly this session, only via search-engine synthesis). The claimed save location for patches above 1.28 (`Saved Games\Warcraft III\` under the user profile) is likewise `[unverified firsthand]`.
Documentation quality: essentially undocumented, needs reverse engineering, confirmed rather than merely assumed: the dedicated Luashine/wc3-file-formats documentation project explicitly lists "save game format" as goal #2 among its own not-yet-started work, and neither its prose nor Kaitai-grammar directories contain any `.w3z`-related file at all (confirmed via direct directory listing).
No open-source tool with confirmed read/write support for `.w3z` was found. A closed-source community tool, "CacheConv" ("War3 Cache Converter"), is repeatedly cited as able to extract the embedded game-cache data from a `.w3z` file to SLK, but per community reports is read-only/extract-only and has no located GitHub repository. inwc3/wc3libs and Drake53/War3Net were both checked directly via GitHub code search for `.w3z`/save-game handling and returned no matches in either repository.
A distinct, better-documented adjacent format, `.w3v` (the "game cache" format used to persist trigger/hashtable variables between campaign missions, not the full engine save-state file), does have partial open-source support in inwc3/wc3libs (`W3V.java`); do not conflate `.w3v` game-cache files with `.w3z` saved-game files, they serve different purposes.

## Suggested implementation order

The dependency graph is layered: lower layers are consumed by every layer above them, so getting them right first avoids rework.

1. **MPQ v1 reader.** Every other format on this list, except `.w3g` replays, lives inside an MPQ archive (base game archives, maps, campaigns). Nothing else can be tested against real WC3 assets until archive extraction works. Scope: v1 only, per the container-formats section above; a v1-only reader is meaningfully smaller than a general-purpose MPQ library and matches WC3's actual behavior exactly.
2. **SLK and TXT gameplay data tables.** These are flat, self-contained text formats with no dependency on the renderer or the JASS VM, and every other gameplay system (unit stats, ability data, upgrades) ultimately reads from them. Parsing these first also gives a natural, low-risk way to validate the MPQ reader against real extracted game data before tackling binary formats.
3. **BLP textures and TGA.** Needed before anything can be rendered; TGA is close to zero additional work given standard decoders exist. BLP0/BLP1 is the WC3-specific subset to target, not BLP2.
4. **MDX/MDL models.** Depends on BLP (materials reference textures) but not on the JASS VM or map internals; can be developed and validated against standalone unit/doodad models extracted straight from the base game MPQs before any map-loading code exists.
5. **The `.w3x`/`.w3m` map container and its per-file formats** (HM3W header, `w3i`, `w3e`, object data files, `war3mapUnits.doo`/`war3map.doo` placement, `wts`, `w3c`, `w3r`, `w3s`, `shd`, `mmp`, `imp`). These depend on the MPQ reader (layer 1) and, for rendering the result, on BLP/MDX (layers 3 to 4), but are otherwise independent of JASS. Terrain (`w3e`) and map info (`w3i`) are the natural starting sub-formats since a map cannot be loaded at all without them. Object data files (`w3u`/`w3t`/`w3b`/`w3d`/`w3a`/`w3h`/`w3q`) should follow before placement data, since `war3mapUnits.doo`/`war3map.doo` entries reference the type IDs those files define; `w3r`/`w3c`/`w3s`/`shd`/`mmp`/`imp` are lower-risk leaves that can come last in this layer.
6. **JASS parsing and the JASS VM**, bootstrapped from `common.j`/`Blizzard.j` (the native declaration surface) and then `war3map.j` (the compiled per-map script). This is the highest-risk, highest-effort layer: it depends on having map loading (layer 5) working first, since a map's JASS references object data and map-scoped globals, and it requires committing to an execution model (tree-walking versus bytecode) informed by prior art like corepunch/open-realm's `libjass`. GUI triggers (`wtg`/`wct`) sit alongside this layer since Blizzard.j is what makes GUI-generated JASS work at all.
7. **FDF/TOC UI definitions.** Lower priority: needed for a faithful in-game UI but not for core simulation correctness, and the base game's own FDF/TOC files can be treated as a fixed, known input rather than something that needs to vary per map in the way object data does.
8. **`.w3g` replay parsing.** Independent of the MPQ layer entirely (custom binary format, not MPQ) but depends on having a correct simulation model (from layers 5 to 6) to actually replay the recorded actions meaningfully; useful primarily as a correctness/regression testing tool once the engine can run games, so it is reasonable to defer until the simulation itself is functional.
9. **Campaign (`.w3f`/`.w3n`) and saved-game (`.w3z`) support.** Lowest priority by a wide margin: `.w3n` is "just" an MPQ containing multiple maps plus a thin `.w3f` metadata file, so it is nearly free once layers 1 and 5 exist; `.w3z` saved games are essentially undocumented and would require dedicated reverse engineering, best deferred until the rest of the engine is stable enough to make that investment worthwhile.
